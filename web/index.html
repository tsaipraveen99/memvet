How it works

MemVet stores a memory as a claim plus the evidence that made it true: the commit, the files, the symbols and their body hashes, and the tests that prove it. On retrieval it re-checks that evidence against the code as it exists now.

Why not just watch files

Files change constantly

A tool that flags every touched file flags a typo fix in an unrelated function, then the next one, and the one after that. It gets muted inside a week.

MemVet keys on qualified symbols and hashes their bodies, so it can tell a docstring from a rewrite, and a rename from a deletion.

Install

$ git clone https://github.com/tsaipraveen99/memvet
$ cd memvet
$ python -m pip install -e .
$ memvet init

# record a decision against the code
# that makes it true
$ memvet remember \
    --title "Validation belongs in the API layer" \
    --file api/handlers.py \
    --symbol api.handlers.validate_order
# what your agent is allowed to rely on
$ memvet context

# re-check every memory against HEAD
# exits non-zero, so it can gate a PR
$ memvet check

# render the findings for review
$ memvet review --base origin/main --json --output web/review.json

Pure standard library in the core path. No model runs in the checking path, so a full pass takes milliseconds. A GitHub Action covers the post-merge surface, and the review viewer turns a report into per-memory verdicts.

What it does not do

MemVet is an evidence-based gate, not a correctness proof.

  • It will not tell you a decision is right. It tells you whether the code it rested on still holds.
  • A claim with nothing to anchor to stays needs_revalidation rather than being quietly promoted.
  • Recording a decision is deliberate. It does not guess what mattered in your session.
  • It does not replace your memory layer. It sits on top of one and checks it.
